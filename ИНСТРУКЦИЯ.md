# BIORYX: единое обновление через браузер

Обновляются существующие репозиторий, Worker и D1. Ничего нового создавать не нужно. Названия пунктов Cloudflare/GitHub могут немного отличаться. Старые промежуточные архивы не устанавливайте. Пока идёт обновление, не принимайте заказы: схемы базы, Worker и витрины должны совпадать. Не размещайте пароли, токены и секреты в GitHub.

## 1. Подготовка и восстановление

1. Распакуйте архив `bioryx-final.zip`. Откройте папку `bioryx`.
2. Запишите адрес сайта, адрес существующего Worker, имя базы D1, имена настроек Worker и версии/копии заменяемых файлов в GitHub и Worker. Убедитесь, что GitHub Actions или Workers Builds не перезапишет ручное изменение Worker из другого источника; если Worker публикуется автоматически, обновлять его нужно в подключённом исходном репозитории этим же файлом.
3. Остановите оформление заказов на время обновления. Создайте доступную вам резервную копию базы и убедитесь, что знаете, как восстановить её. Cloudflare D1 Time Travel включён автоматически для production backend, но официальная инструкция восстановления использует Wrangler, то есть терминал: https://developers.cloudflare.com/d1/reference/time-travel/ . Если вы не можете обеспечить восстановление без терминала — не начинайте миграцию; сначала обратитесь к человеку с доступом к восстановлению либо в поддержку Cloudflare. Запишите точные дату, время с часовым поясом непосредственно перед изменениями. Восстановление откатывает всю базу, включая данные, появившиеся после выбранного времени.
4. В Cloudflare → Workers & Pages → D1 SQL Database выберите **существующую** базу. Не создавайте новую. `worker/setup.sql` не выполнять: в нём стартовые данные.

## 2. Миграции D1

1. Откройте Console базы. У нас нет сведений о фактически установленных миграциях; порядок нельзя угадывать. Определите последнюю успешно и полностью установленную версию по вашим предыдущим действиям и истории SQL. Если не уверены — остановитесь и пришлите список таблиц и историю, прежде чем продолжать. Одно наличие таблицы не доказывает, что вся миграция полностью выполнилась.
2. В папке `worker/migrations/` откройте текстовым редактором первую ещё не применённую миграцию и скопируйте её содержимое в D1 Console, нажмите Execute/Run. Затем делайте следующую строго по номеру до `0023_promo_extra_conditions.sql` включительно. Не выполняйте 0001–0003 повторно и не используйте объединённый `upgrade-existing.sql`, если неизвестно, что из него уже применялось. Если ваша база действительно полностью остановилась на 0003, выполняйте 0004, 0005 … 0023. Если уже установлена 0022, нужна только 0023.
3. При ошибке остановитесь, запишите имя файла, текст ошибки и что было выполнено. Не запускайте оставшиеся миграции и не повторяйте наугад: часть команд могла выполниться. Если консоль не принимает многострочный файл целиком или триггер — остановитесь; не делите триггеры по точкам с запятой. Нужен поддерживаемый способ выполнения всей миграции или помощь с D1. Не удаляйте таблицы и не нажимайте сброс базы.

## 3. Существующий Worker

1. Cloudflare → Workers & Pages → откройте действующий Worker. Сохраните прежний код и настройки. Проверьте, что имя D1 binding — `DB` и оно указывает на ту же базу, где выполнялись миграции.
2. Откройте Edit code / Quick edit. Если редактор Worker состоит из одного основного файла, полностью замените его содержимое файлом `worker/src/index.js`, сохраните и Deploy. Панель уже встроена в этот файл: отдельно `admin.html` загружать не требуется. Если включена автоматическая сборка из GitHub, измените именно файл источника этого Worker в соответствующем репозитории и дождитесь его автоматической публикации; не меняйте имя Worker или привязку базы. При ошибке публикации сохраните сообщение и остановитесь.
3. В Settings → Variables and Secrets убедитесь, что сохранены `SITE_URL` (полный адрес сайта, включая путь проекта и завершающий `/`), `OWNER_BOT_TOKEN`, `OWNER_CHAT_ID`, `CUSTOMER_BOT_TOKEN`, `WEBHOOK_SECRET`, `ADMIN_PASSWORD` (минимум 16 символов) и `ADMIN_SESSION_SECRET` (минимум 32 символа). Токены и секреты добавляйте как Secret, не в репозиторий. Старые правильные значения не меняйте. На случай изменений конфигурации убедитесь, что публикация применена. Для обработки очередей в Triggers должен быть Cron, например `*/5 * * * *`.
4. Если существующий webhook клиентского Telegram-бота уже указывает на тот же Worker, повторная настройка не нужна. Если нужно настроить: создайте временный секрет `SETUP_SECRET`, откройте `https://АДРЕС-WORKER/setup`, введите его и выберите настройку webhook; затем удалите `SETUP_SECRET`. Токены никому не отправляйте. Бот пользователя должен быть запущен командой /start, а владелец должен начать диалог с ботом владельца.

## 4. Обновление сайта на GitHub

1. На компьютере откройте `assets/config.js` и впишите полный адрес существующего Worker без завершающего `/` в `window.BIORYX_API`, а имя клиентского Telegram-бота без `@` — в `window.BIORYX_BOT`. Сохраните. Не вписывайте токены.
2. Откройте существующий репозиторий GitHub и ту ветку/папку, из которой публикуется сайт. Через Add file → Upload files загрузите и замените файлы **изнутри** папки `bioryx`, сохраняя относительные пути: корневые HTML, каталог `assets` и каталог `data`. Не вкладывайте их в дополнительную папку `bioryx`, если сайт прежде был в корне. Через веб-интерфейс может понадобиться загружать файлы по каталогам: сначала откройте нужный каталог на GitHub, затем Upload files. Подтвердите Commit changes. `worker`, `tools`, `docs` на сайт загружать необязательно; но если этот же репозиторий автоматически собирает Worker, обновите и используемый им файл Worker в его исходном пути, как в пункте 3.
3. Дождитесь публикации GitHub Pages / Cloudflare Pages в Actions или Deployments, откройте текущий адрес сайта, обновите страницу. Панель: адрес Worker + `/admin`.

## 5. После публикации

Акции создаются в панели в разделе промо. Дополнительные условия: обязательный вход, первый привязанный заказ, персональный лимит, обязательный товар и его количество. 0 означает отсутствие персонального лимита. Первый привязанный заказ — отсутствие других заказов, сделанных после входа; старые гостевые заказы не распознаются. Лимиты учитывают и отменённые заказы. Подарок не считается обязательным товаром. Условия вы зададите позже.

Заказы и клиенты, существовавшие до обновления, должны оставаться в той же D1. Кэшбэк начисляется при одновременных статусах «доставлен» и «оплачен» и пересчитывается при выходе из этого состояния. Смена статусов не переводит и не возвращает деньги. СБП подтверждается вручную; стоимость доставки и СДЭК согласуются вручную, интеграции перевозчика нет. Старые гостевые заказы автоматически к Telegram не привязываются. Отчёты не являются бухгалтерской прибылью; экспорт содержит персональные данные. Товары, цены и изображения в комплекте демонстрационные.

Реальная D1, Telegram, одновременные заказы и браузер в вашей среде не проверены. До открытия реальных продаж нужны отдельные практические испытания, проверка безопасности, обработки персональных данных и юридических документов. При проблеме не выполняйте массовые SQL-повторы и пришлите шаг, текст ошибки и скриншот без секретов.
